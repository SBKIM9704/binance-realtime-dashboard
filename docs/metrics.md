# 대시보드 지표 정의와 선택 근거

이 대시보드는 **운영 팀 관점**에서 만들어졌습니다. 목표는 두 가지입니다.

1. **수집 파이프라인이 건강한가?** — 데이터가 끊김 없이, 지연 없이, 완결성 있게 들어오는가
2. **시장은 지금 어떤 상태인가?** — 수집된 데이터로 즉시 파악 가능한 시세/거래 현황

"운영 대시보드"의 핵심은 **데이터를 신뢰할 수 있는가**입니다. 시세 지표가 아무리 예뻐도
수집이 20분 밀려 있거나 캔들에 구멍이 뚫려 있으면 그 위의 모든 판단이 틀립니다.
그래서 시세 지표보다 **파이프라인 건강 지표를 1급 시민으로** 배치했습니다.

---

## A. 파이프라인 운영 지표 (Ops)

| 지표 | 정의 | 왜 보는가 |
|------|------|-----------|
| **WS 연결 상태** | 심볼별 WebSocket 연결 여부(connected/disconnected) | 실시간 수집의 생사. 끊기면 즉시 조치 필요 |
| **수집 지연 (lag)** | `현재시각 − 최신 캔들의 close_time` | 데이터 신선도. lag이 커지면 WS 지연/중단 신호. 대시보드 판단 신뢰도의 직접 척도 |
| **총 레코드 수** | 심볼별 저장된 kline 개수 | 수집량/커버리지 확인. 백필·재시작 후 누적 상태 |
| **백필 건수** | 최초/재시작 백필로 채운 캔들 수 | 부팅 시 누락 복구가 실제로 동작했는지 확인 |
| **결측(gap) / 채움** | reconciler가 탐지한 결측 버킷 수와 채운 수 | 데이터 완결성. WS 순간 단절이 자동 복구되는지 |
| **reconciler 마지막 실행** | 마지막 결측 스캔 시각 | 자가 치유 루프가 살아있는지 |
| **최근 이벤트 타임라인** | 연결/해제/백필/gap/에러 로그 | 운영 사고의 타임라인. 무슨 일이 언제 있었는지 사후 추적 |

### 왜 이 지표들인가
- **lag과 gap은 "데이터 신뢰도"를 수치화**합니다. 운영팀이 가장 먼저 봐야 할 값입니다.
- **백필/reconciler 지표는 요구사항(최초 실행·재시작 누락 백필)이 실제로 작동함을 증명**합니다.
  단순히 구현했다가 아니라, 대시보드에서 복구가 눈에 보이게 했습니다.
- **이벤트 타임라인**은 장애 발생 시 원인 추적(post-mortem)에 필요한 최소 관측성(observability)입니다.

## B. 시세 / 거래 지표 (Market)

| 지표 | 정의 | 왜 보는가 |
|------|------|-----------|
| **실시간 가격** | 최신 1m 캔들의 종가 | 현재 시세. 가장 기본 |
| **24h 변동률** | `(현재가 − 24시간 전 종가) / 24시간 전 종가` | 하루 흐름. 급등락 감지 |
| **24h 거래량** | 최근 1440개 1m 캔들 거래량 합 | 유동성/관심도. 거래량 급증은 변동성 선행 신호 |
| **변동성** | 최근 N분 로그수익률의 표준편차(연율화 전 원값) | 리스크 수준. 운영/투자 판단 모두에서 핵심 |
| **Bid / Ask** | `@bookTicker` 스트림의 최우선 매수/매도 호가 | 실시간성 확인 + 체결 가능 가격대 |
| **Spread** | `(Ask − Bid) / Bid` | 유동성 판단. 스프레드 확대 = 유동성 악화 신호 |
| **VWAP (24h)** | `Σ quoteVolume / Σ volume` (24h) | 거래량 가중 평균가. 체결 품질/기준가 판단에 실무 사용 |
| **24h High / Low** | 최근 1440개 캔들의 max(high)/min(low) | 당일 레인지. 사용자가 가장 자주 보는 값 |
| **가격 차트** | 1m 종가 라인 + 거래량 바 | 추세/모멘텀을 시각적으로 파악 |
| **최근 캔들 테이블** | 최신 OHLCV 원자료 | 원천 데이터 직접 확인(디버깅/검증) |

### 왜 이 지표들인가
- **가격·변동률·거래량**은 시장 상태를 한눈에 요약하는 표준 3종 세트입니다.
- **변동성**을 추가한 이유: 운영 관점에서 변동성 급증은 곧 트래픽/리스크 급증을 의미하며,
  투자 판단에도 직접 쓰이는 지표라 "운영+투자" 양쪽에 걸칩니다.
- 모든 시세 지표는 **우리가 수집·저장한 데이터에서 계산**합니다(외부 티커 API 재호출 없음).
  이는 "수집한 데이터로 대시보드를 만든다"는 과제 취지에 부합하고, 수집 품질이 곧
  지표 품질로 이어지므로 A 섹션(파이프라인 건강)의 중요성을 다시 강조합니다.

## C. 시스템 지표 (System)

수집기는 장시간 상주하는 프로세스이므로, 운영자는 **서버 자원과 API 사용량**을 함께 봅니다.
(운영자 시선 흐름: **System → Pipeline → Market**)

| 지표 | 정의 | 왜 보는가 |
|------|------|-----------|
| **CPU / RAM** | 수집기 프로세스 CPU% · RSS 메모리 | 상주 프로세스의 자원 누수/과부하 조기 감지 |
| **Uptime** | 프로세스 가동 시간 | 재시작 여부/안정성 |
| **REST calls/min** | 분당 REST 호출 수 | 호출량 추세 |
| **REST Weight** | `used-weight / 6000` (Binance IP 예산) | Rate limit 임박 여부를 즉시 판단 |
| **REST Retry / 429 / 5xx** | 재시도·rate limit·서버 에러 누적 | 장애 시 가장 먼저 보는 숫자 |

> Weight·에러 지표는 [`rate-limits.md`](rate-limits.md)의 안전장치와 직접 연결됩니다.

## D. 임계값 (Alert Thresholds)

각 지표는 **"언제 조치해야 하는가"** 기준으로 초록/노랑/빨강 색상 코딩됩니다.
구현: [`src/lib/thresholds.ts`](../src/lib/thresholds.ts) (단위 테스트 `thresholds.test.ts`).

| 지표 | 🟢 정상 | 🟡 경고 | 🔴 위험 |
|------|--------|--------|--------|
| WS 연결 상태 | Connected | — | Disconnected |
| 수집 지연 (Lag) | < 5초 | 5–30초 | > 30초 |
| Msg Rate | 연결 & 수신 중 | — | 연결됐으나 0 msg/s |
| Gap Recovery Rate | 100% | 95–99% | < 95% |
| REST Weight | < 70% | 70–90% | > 90% |
| Error Rate | 0 /min | 1–5 /min | > 5 /min |

이 기준 덕분에 대시보드는 단순 정보 표시를 넘어, **운영자가 즉시 판단·대응할 수 있는 운영 도구**가 됩니다.

## 데이터 기준
- **수집 단위:** 1분봉(kline). 실시간성과 저장/조회 효율의 균형점.
- **계산 기준:** 24h = 최근 1440개 1m 캔들, 변동성 = 최근 30분 로그수익률 표준편차(설정 가능).
- **신선도:** SSE로 1초 주기 스냅샷 push → 대시보드는 항상 최신 저장 상태를 반영.
