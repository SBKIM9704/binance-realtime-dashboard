# 대시보드 지표 — 선택 근거와 임계값

> 과제 요구사항 *"해당 지표를 선택한 이유와 근거를 간단한 문서로 남겨 주세요"*에 대한 답입니다.
> 요약은 [README의 대시보드 지표 절](../README.md#-대시보드-지표)에 있습니다.

## 설계 원칙

1. 운영자는 가장 먼저 **시스템 상태**를 확인할 수 있어야 한다.
2. 시장 데이터보다 **데이터 품질**을 우선한다.
3. 모든 지표는 **출처를 추적**할 수 있어야 한다.
4. 장애는 숨기지 않고 **즉시 드러나야** 한다.

투자 화면이 아니라 운영 화면이므로 지표 선정 기준은 "수집 품질을 먼저 확인할 수 있는가"이며,
**System → Pipeline → Market** 3계층으로 구성했습니다.

<br />

## 1. 데이터 흐름

```
  Binance
     │  WebSocket (kline_1s + bookTicker) · REST (backfill)
     ▼
  Collector ──────────── 백필 · 재연결 · reconciler · 히스토리 티어
     │
     ▼
  Storage (SQLite/WAL)   klines(symbol, interval, open_time)
     │
     ▼
  Aggregator ──────────── 조회 시점 SQL 롤업 · 티어 선택
     │
     ▼
  API                    /api/stream(SSE) · /api/candles · /api/health
     │
     ▼
  Dashboard              마켓(/) · 운영 현황(/ops)
```

집계는 **저장 이후·API 이전** 단계에 있습니다. 큰 봉을 따로 수집하지 않고 조회 시점에
만들기 때문에, 화면에 인터벌을 추가해도 수집기와 스키마는 그대로입니다.

<br />

## 2. 데이터 계층 (Tier)

**티어**란 같은 종목을 서로 다른 시간 해상도로 저장한 것입니다. 정밀할수록 보관 비용이 커지므로,
정밀도와 기간을 맞바꾼 세 층을 함께 둡니다.

```
  1s   정밀 ▲   보관 7일        ← 운영 감시 (수집기가 돌아간 구간만 존재)
  1m           보관 30일        ← 1일~1개월 차트 · 24h 지표 집계
  1h   조밀 ▼   상장일부터       ← 1년 · 전체 차트
```

| 티어 | 보관 | 성격 | 실측 행 수 (심볼당) |
|------|------|------|----------|
| `1s` (수집 인터벌) | 7일 | 정밀하지만 얕고, 수집기 중단 구간에 결측이 생길 수 있음 | 3일치 259,200 |
| `1m` | 30일 | REST 백필이라 조밀 | 43,201 |
| `1h` | 2017-08-17부터 전체 | REST 백필이라 조밀 | 78,405 |

1초봉만으로는 전체 역사를 담을 수 없어 이 구조가 필요합니다 — BTCUSDT 9년치 1초봉은 약 2억
8천만 개, 25GB입니다. 같은 기간을 1시간봉으로는 78,405행에 담습니다.

조회 시에는 **요청한 봉 크기를 정수배로 나누면서, 그 구간을 덮고, 충분히 조밀한 가장 정밀한
티어**가 자동 선택됩니다(`src/lib/source-interval.ts`).

## 3. 데이터 품질 원칙

지표 선정의 기준이 된 데이터 품질 정의입니다.

| 원칙 | 정의 | 대응 지표 · 장치 |
|------|------|-----------------|
| **① Complete** | 데이터는 빠지지 않아야 한다 | 복구율 · 탐지/복구 수 · reconciler · 백필 |
| **② Fresh** | 실시간이어야 한다 | 지연(Lag) · Msg/s · 프레임 신선도 · 호가 경과 시간 |
| **③ Accurate** | 집계는 정확해야 한다 | 조밀 티어 기반 24h 집계 |
| **④ Traceable** | 출처를 알 수 있어야 한다 | 집계 티어 표시 · 최근 캔들 원자료 · 이벤트 로그 |

## 5. System 지표 — 수집기 프로세스와 API 예산

| 지표 | 선택 근거 | 🟢 | 🟡 | 🔴 |
|------|----------|----|----|----|
| **CPU · RAM · 업타임** | 상주 프로세스의 기본 건강. 업타임은 크래시 루프를 드러냄 | — | — | — |
| **REST 호출/분** | 백필·정합이 REST를 얼마나 쓰는지 | — | — | — |
| **REST Weight** | Binance는 요청 수가 아니라 **weight로 제한**(6000/분). 초과 시 IP 차단 | < 70% | 70–90% | > 90% |
| **재시도 / 429 / 5xx** | 429는 이미 한도를 건드렸다는 신호, 5xx는 거래소 측 장애 | 0 | 발생 | — |

**Weight 임계 근거.** 70%는 남은 30%로 진행 중인 백필을 완주할 수 있는 여유 구간이고, 90%는 한
번의 대량 백필로도 한도를 넘길 수 있는 지점이라 위험으로 둡니다. 대량 백필은 조용히 한도에
접근하다 한순간에 차단되며, 차단을 알아챘을 땐 이미 데이터가 비어 있습니다.

## 6. Pipeline 지표 — 수집이 정상인가

| 지표 | 선택 근거 | 🟢 | 🟡 | 🔴 |
|------|----------|----|----|----|
| **WS 연결** | 수집의 생사. 끊기면 나머지는 전부 과거 데이터 | 연결 | — | 끊김 |
| **Msg/s** | **연결됐지만 조용한 상태**를 잡는 지표. WS는 살아 있는데 데이터가 안 오는 장애가 실재함 | > 0 | — | 0 |
| **지연(Lag)** | 마지막 캔들이 얼마나 뒤처졌나. 실시간성의 직접 측정 | < 5초 | 5–30초 | > 30초 |
| **복구율** | 탐지한 결측 중 실제로 채운 비율. 완결성의 핵심 지표 | 100% | 95–99% | < 95% |
| **탐지 / 복구 수** | 복구율의 분모·분자. 비율만 보면 "1건 중 1건 = 100%"를 구분 못 함 | — | — | — |
| **재연결 횟수** | 네트워크 불안정의 누적 신호 | — | — | — |
| **에러/분** | 최근 1분 에러 발생률 | 0 | 1–5 | > 5 |
| **총 레코드** | 전 티어 누적 저장량 (실시간 인터벌 수치 병기) | — | — | — |
| **이벤트 로그** | 위 숫자들의 시간축 기록. 복구율이 떨어진 경위는 로그에만 남음 | — | — | — |

**임계값 근거.**

- **지연 5초** — 1초 단위 수집 기준 **캔들 5개 이상이 누락될 수 있는 시점**으로 정의했습니다.
  그 아래는 네트워크 지터 범위이고, 30초를 넘으면 reconciler 주기(60초) 안에 자동 복구되지
  않을 가능성이 커집니다.
- **복구율 95%** — 100% 미만은 이미 데이터에 구멍이 남아 있다는 뜻입니다. 95%는 **복구 실패가
  누적되기 시작하는 구간**으로 보아 운영 경고 기준으로 사용했습니다.
- **에러 0/분** — 정상 운영에서 에러는 0이어야 하므로 발생 자체를 경고로, 분당 5건 초과는
  재시도로 해소되지 않는 상태로 봅니다.

임계값은 화면의 값 옆에 함께 표시됩니다(`0.8s` `< 5s`).

## 7. Market 지표

| 지표 | 선택 근거 |
|------|----------|
| **실시간가** | 파이프라인이 살아 있다는 가장 직접적인 증거 |
| **24h 변동률** | 단일 숫자로 "오늘 시장이 어느 쪽인가"를 답하는 표준 지표 |
| **24h 고가/저가** | 현재가의 위치를 하루 범위 안에서 맥락화 |
| **24h 거래량** | 가격 변동에 실체가 있는지 판별. 거래량 없는 급등은 신뢰할 수 없음 |
| **VWAP** | 거래량 가중 평균가. "지금 가격이 오늘 평균보다 비싼가"에 답함 |
| **변동성** | 단기 리스크 크기. 같은 1% 움직임도 변동성이 낮을 때가 더 유의미 |
| **Bid/Ask · 스프레드** | 유일한 **비(非)캔들 실시간 지표**(`@bookTicker`). 체결 비용을 즉시 반영 |
| **최근 캔들 테이블** | 집계된 숫자의 원본. 화면 값을 행 단위로 대조 가능 |

### 7.1 24h 집계를 어느 티어에서 계산하는가

처음에는 24h 집계를 수집 인터벌(1초봉)에서 계산했습니다. 그런데 1초봉은 수집기가 실제로 돌아간
구간만 존재하므로, 중단됐던 시간만큼 구멍이 뚫립니다.

Binance 공표치와 대조한 실측 오차입니다.

| 지표 | 1초봉 기준 | 조밀 티어 기준 |
|------|-----------|--------------|
| 24h 거래량 (BTC / ETH) | **−35.1% / −59.7%** | −0.032% / −0.039% |
| 24h 저가 (ETH) | +1.9% (저점을 놓침) | 0.000% |
| VWAP | −0.8% | −0.000% |

1초봉 기준 수치는 티어 도입 전 측정값이고, 조밀 티어 기준 수치는 현재 구현을 `/api/v3/ticker/24hr`
공표치와 대조한 값입니다. 거래량 잔차는 24h 경계 정렬 차이에서 발생합니다.

운영 환경에서는 완결된 데이터가 집계 정확도에 직접적인 영향을 주므로, 24h 집계는 해당 구간을
덮으면서 조밀한 티어에서 계산합니다(`pick24hSource`). 1초봉은 원래 목적인 수집 품질 감시에
사용합니다.

## 8. 장애 시나리오와 대시보드 반응

각 장애 상황에서 화면이 실제로 어떻게 반응하는지입니다.

| 상황 | 대시보드 반응 |
|------|--------------|
| **WS 끊김** | 종합 상태 🔴 · 해당 심볼 건강 점 빨강 · 이벤트 로그에 `WS 해제` 기록 |
| **WS는 연결됐으나 데이터 없음** | Msg/s 0 → 🔴 (연결 상태만 보면 놓치는 장애). 수집기가 살아 있으면 `flushStats`가 1초마다 계속 돌아 수신량이 0으로 떨어짐 |
| **수집기 프로세스 강제 종료** | Lag 🔴 → 종합 상태 🔴. 단 **WS·Msg/s는 마지막 값에서 정지** — 상태 행을 갱신할 프로세스가 없음. 아래 한계 참조 |
| **수집 지연 발생** | Lag 🟡→🔴, 임계값(`< 5s`)이 값 옆에 함께 표시 |
| **결측 발생 → 복구 성공** | 복구율 100% 유지 🟢 · 탐지/복구 수 동시 증가로 발생 사실은 남음 |
| **결측 발생 → 복구 실패** | 복구율 하락 🟡→🔴 |
| **REST 한도 근접** | Weight 🟡→🔴 · 소프트 임계 초과 시 수집기가 선제적으로 페이싱 |
| **SSE 종료 (웹↔서버 단절)** | 3초 후 종합 상태 🔴 · `연결 끊김 · 마지막 수신 N초 전` · 모든 수치 흐림 처리 |
| **호가 갱신 중단** | Bid/Ask 옆 경과 시간이 빨강으로 전환 |
| **해당 구간 데이터 없음** | 차트가 빈 캔버스 대신 "저장된 캔들이 없습니다 · N부터 데이터가 있습니다" 안내 |

SSE 종료 · 호가 갱신 중단 · 데이터 없음 항목이 **설계 원칙 4번**의 구현입니다. 프레임 신선도를
검사해, 신선도를 잃은 값은 화면에서 시각적으로 구분됩니다.

> **알려진 한계 — 수집기 프로세스 죽음.** `SIGKILL`로 재현해 확인한 동작입니다. 정상 종료
> (`SIGINT`/`SIGTERM`)는 셧다운 훅이 `wsConnected = 0`을 기록하지만, 강제 종료에는 그 훅이 돌지
> 않아 `ws_connected = 1`과 마지막 `ws_msg_rate`가 DB에 그대로 남습니다. 이후 `/ops`는 30분이
> 지나도 해당 심볼을 **WS 🟢 실시간 · Msg/s 🟢 (마지막 값)** 으로 표시합니다.
>
> 종합 판정은 정확합니다 — `lagMs`가 `lastKlineOpenTime` 기준으로 계속 벌어져 Lag가 🔴이 되고,
> 리본의 `worstTier`가 이를 집어 전체를 위험으로 올립니다. 다만 심볼 단위 신호 5개 중 2개가
> 사실과 다른 값을 보이고, 운영자는 *수집기가 죽은 것*과 *스트림만 조용한 것*을 Lag 하나로는
> 구분할 수 없습니다(조치가 다릅니다 — 프로세스 재시작 vs 네트워크·거래소 확인).
>
> 해결책은 이미 저장 중인 `pipeline_status.updated_at`입니다. 수집기가 마지막으로 행을 쓴
> 시각이므로 `now - updated_at`이 곧 프로세스 하트비트이고, 이 값이 오래된 심볼의 WS·Msg/s를
> 신뢰하지 않도록 강등하면 두 장애가 분리됩니다. 현재는 SSE 프레임에 실려 나가지만 화면이
> 읽지 않습니다.

## 9. 표시 방식 선택

| 방식 | 쓴 곳 | 이유 |
|------|------|------|
| **캔들 차트** | 가격·거래량 | 결측 구간이 **빈 봉으로 드러남**. 선 그래프는 구멍을 이어버려 수집 문제를 감춤 |
| **숫자 카드** | 시세 · System · Pipeline | 단일 값의 즉시 판독. 색상 코딩과 결합 |
| **스파크라인** | 종목 카드 | 축 없이 최근 추세 방향만 전달 |
| **테이블** | 최근 캔들 · 이벤트 로그 | 시간순 원본 데이터 검증 |
| **리본** | 종합 상태 | 항상 보이는 한 줄 요약 |

등락 색은 언어 관례를 따릅니다 — 한국어 UI는 상승 빨강 / 하락 파랑, 영어 UI는 초록 / 빨강
(`src/lib/trend.ts`에 단일 정의).

## 10. 의도적으로 넣지 않은 것

| 항목 | 이유 |
|------|------|
| **호가창 깊이(depth)** | `@bookTicker`는 최우선 호가만 제공. 깊이는 별도 스트림이 필요하고 저장량이 급증 |
| **기술적 지표(MA·RSI 등)** | 운영 도구의 범위 밖. 파생 지표는 수집 품질 신호를 가림 |
| **알림·경보** | 임계값 색상까지가 이번 범위. 알림은 전달 채널·중복 억제·에스컬레이션이 따라붙는 별도 설계 |
| **일/주/월 캔들 뷰** | 기본 보존이 7일이고, 일봉 경계가 UTC 자정이라 국내 거래소 일봉과 하루가 어긋나 보임 |

## 부록 A. 표시 단위 설계

두 지표는 계산은 맞았지만 표시 단위 때문에 정보를 전달하지 못해 단위를 변경했습니다.

**변동성 → 백분율 대신 bp(베이시스 포인트).**
원값은 로그수익률 표준편차로 약 `4e-5`입니다. 백분율에 소수 2자리로 표시하면 항상 `0.00%`가 되어
값을 비교할 수 없습니다. bp로 표기하면 `3.05 bp`처럼 구분 가능한 숫자가 됩니다. 24h 지표들과 같은
줄에 놓이므로 라벨에 산출 구간을 함께 표기합니다(`변동성 (1시간)`).

**스프레드 → 백분율 대신 틱(tick).**
BTCUSDT·ETHUSDT는 유동성이 높아 스프레드가 대부분 1틱(0.01 USDT), 즉 최소 단위입니다. 백분율로는
`0.000%`/`0.001%`만 반복되어 변화를 읽을 수 없습니다. 틱 단위로 표기하면 `1틱`이 기준값이 되고
`3틱`은 스프레드 확대로 즉시 식별됩니다. 백분율은 참고로 병기합니다.

> 틱 크기는 Binance `exchangeInfo`의 `PRICE_FILTER` 값이며 `src/lib/market-meta.ts`에 상수로
> 관리합니다. 심볼 추가 시 등록이 필요합니다.
